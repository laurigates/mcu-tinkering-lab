# robocar: WiFi provisioning and OTA

Moved word for word from the project `CLAUDE.md`, which keeps a
one-line form of each rule below and links here for the reasoning.

## WiFi provisioning

Uses **Improv WiFi Serial** provisioning by default — no credentials compiled in. `CMakeLists.txt` auto-generates a stub `credentials.h` at configure time if one doesn't exist, so CI and the web flasher don't need credentials. For local dev with hardcoded creds, copy `main/credentials.h.example` to `main/credentials.h` (gitignored).

It is the **Serial** variant of Improv (the `improv-wifi` component implements the Improv Serial spec), not BLE. `init_network()` installs the parser on every boot, and the network supervisor arms it — `command_task` then feeds every console byte to it, and the parser ignores anything that is not a well-formed Improv packet — when the board has no stored credentials, or when the link has been down for `NET_IMPROV_REARM_MS` (2 min), and disarms it on reconnect. Credentials reach NVS only after the link comes up with them: the Improv callback starts the attempt and returns, and the supervisor saves them on `GOT_IP` or sends `UNABLE_CONNECT` once the fast retries are spent, then rejoins the stored network.

**Nothing waits on WiFi** (issue #846). `wifi_connect()` starts an attempt and returns; driver errors are logged, never `ESP_ERROR_CHECK`ed. The console, the executor and the reflex come up while WiFi is still connecting. `net_supervisor_task()` in `main.c` polls the link every 500 ms and carries out what `net_supervisor_core.c` decides: OTA, with its rollback-confirm timer, starts on the first link-up of the boot; MQTT starts on every link-up and stops on every link-down (`mqtt_logger_pause()`/`resume()`). The client itself is created at boot by `create_mqtt_client()`, before the supervisor starts, and is not connected until the first link-up (ADR-028 §2): that first link-up runs `ota_manager_init()` before MQTT starts, and `mqtt_logger_subscribe()` refuses until the client exists, so creating it on link-up dropped the OTA check-now subscription (issue #1054, pinned by `test_mqtt_logger.c`). `CONFIG_MQTT_SKIP_PUBLISH_IF_DISCONNECTED=y` keeps esp-mqtt from queueing publishes while the client is stopped. Improv arms and disarms as above. It used to be one check at boot, so a board that booted offline never got MQTT or OTA, and an OTA image whose first boot was offline was never confirmed and rolled back. With no link the planner, `narrate`, voice turns and TTS make no request, so an offline hour spends no planner or voice-turn fuse. `test_net_supervisor_core.c` pins the decisions, including an offline hour and the uint32 millisecond wrap; the ESP glue is bench work.

**Both directions ride the USB-Serial-JTAG console, and both bypass its line-ending translation** (`improv_console.c`, issue #644). The shared component writes UART0 by default, which on the XIAO is D6/D7 — not the console, and at the time not initialised — so from the day Improv was wired in (#429, 2026-07) requests arrived over USB and every reply went nowhere. `init_network()` now hands it `improv_console_write()` before `improv_wifi_init()`. That writer holds the stdout and stderr stream locks, switches the VFS TX translation to LF for one `write()` and restores it, because the default LF→CRLF mapping would insert a 0x0D before any 0x0A in a binary packet. It then `fsync()`s, because the non-driver VFS pushes its 64-byte TX FIFO to the host only when it writes a `\n`, so without it a reply's tail waits for the next log line. On the input side `command_task` calls `improv_console_raw_input()`, since the default CR→LF mapping turns a 0x0D in a request — the length byte of any 13-character SSID or password — into 0x0A. `test_improv_wifi.c` pins the component half (which transport a reply takes, one write per packet, a writer set before init surviving it); the console half is ESP-only and can only be checked on a bench, with ESP Web Tools' "Connect to Wi-Fi" flow.

**The component speaks the protocol ESP Web Tools speaks** (issue #1056). Until then it framed packets differently from the spec and from `sdk-serial-js`, the client ESP Web Tools runs: its checksum left out the `IMPROV` header, RPC commands and results had no data-length byte, RPC 0x02 was treated as *Identify* (a BLE command; the serial 0x02 is *Request current state*, which the client sends to detect Improv at all), and "unable to connect" was 0xFE (the client's own timeout code) instead of 0x03. So no ESP Web Tools session could have completed against it. Request current state answers with the last state the firmware sent, and replays the provisioning result when provisioned. Request device info returns the project's `flasher.json` `name` (read by the component's `CMakeLists.txt`, the same field the web-flasher manifest uses, so ESP Web Tools offers *Update* rather than an erasing *Install*), the image version, the chip family and the project name. `test_improv_wifi.c` checks each against the spec's bytes; bench acceptance is still ESP Web Tools' "Connect to Wi-Fi".

**A credentials packet never becomes a console line.** `command_task` logs every completed line as `Serial cmd:`, and the log goes on to the UART0 mirror and the GlitchTip breadcrumb ring, so a Send Wi-Fi settings packet assembled into a line would carry the Wi-Fi password to all three. `improv_wifi_process_byte()` returns true for every byte of a packet from the one completing the `IMPROV` header through the checksum, and `console_line_feed()` (`console_line.c`) drops its partial line on such a byte and never stores one. That also keeps a 0x0A or 0x0D inside a packet from ending a line early, and a checksum byte from being dispatched as a one-letter movement command. `test_console_line.c` runs both, unmodified, on the bytes ESP Web Tools sends.

**A packet cut by a link edge, stalled or rejected leaks nothing either** (issue #1087). The parser is fed while Improv is armed, and while it finishes a packet that was in flight at a disarm (below), and a link edge can land in the middle of a packet. Before #1087, a packet cut off by an edge left the parser mid-packet: on the next arm it spent the stale length on the next packet, took one of its bytes as the checksum, failed, and returned false for the rest, so the password reached the line and the log. The fix rests on one property of the client: sdk-serial-js, which ESP Web Tools runs, writes each packet in one call, so a packet arrives as one burst of bytes, and a gap longer than `CONSOLE_LINE_BURST_GAP_MS` (300 ms) ends a burst. `command_task` passes each byte's read time to `console_line_feed()`, which runs the parser itself on `command_task`, and:

- **Finishes a packet in flight across an edge.** The network supervisor bumps `s_improv_session` on each arm and disarm (odd while armed), so an edge between two bytes, or a disarm and re-arm, is always seen. If the parser has started on a packet at that point, including when it has matched only some of the `IMPROV` header and claimed nothing yet, it keeps being fed until that packet ends, since the remaining bytes, a 0x0A length byte among them, cannot be told from text without it. `improv_wifi_parser_idle()` tells a partly matched header from text.
- **Drops the rest of the burst after any packet.** After a well-formed packet that is its trailing newline. After one the parser rejected (a length byte too small, or a packet that lost framing) it is the rest of that packet, 0x0A and 0x0D bytes included. A new header inside the dropped burst still parses, so two packets in one write both land.
- **Resets the parser at a gap inside a packet, and drops the burst that follows.** A disarm and re-arm take two supervisor steps, 500 ms apart, so a packet split by both always shows such a gap. Either the packet was cut off for good and a new one follows, which parses from its own header, or it stalled and its tail follows, which is dropped; that packet is not delivered and the client times out and retries. A partly matched header is kept across a gap: the parser drops it on the first byte that does not continue it, and a stalled header completes as normal. After a gap longer than `CONSOLE_LINE_PACKET_STALE_MS` (5 s) the packet counts as dead and the burst that follows is text, so a command typed after an aborted provisioning runs (issue #1103); the price is that a tail delayed by more than 5 s would become a line, Wi-Fi password included, and be logged.

The gap must outlast `command_task`'s 100 ms sleep when `getchar()` finds nothing (`TASK_DELAY_SHORT_MS`), which a packet split across two USB transfers can wait out between two of its bytes; `main.c` asserts it is at least twice that. Two limits remain, and neither puts a packet byte into a line: a command typed within 300 ms of a packet is dropped with its burst, as is the first command typed up to 5 s after a packet cut off inside its frame, and a packet stalled by 300 ms or more is not delivered. The 5 s staleness limit adds a third, which can: a packet tail that arrives more than 5 s after its packet was cut is read as text. A client that paused for longer than the gap more than once inside one packet would break the property the fix rests on, and its later bytes would be read as text. `test_console_line.c` cuts a credentials packet after every byte, for a disarm, a disarm with the rest stalled, and a disarm plus re-arm with and without the gap, and asserts that no line holds a byte of it.

**The announcement repeats the remembered state.** `command_task`'s 1 Hz announcement is `improv_wifi_announce()`, which re-sends the last state, so during a connect attempt it keeps saying Provisioning (it used to send Ready, which RPC 0x02 then reported while the board was still connecting). A failed attempt goes through `improv_wifi_fail_provisioning()`, which sends the error and returns to Ready, and arming resets the state to Ready, since it may still be Provisioned from an earlier session. The component half is in `test_improv_wifi.c`; the `main.c` call sites are bench work.

Because the planner is non-fatal, a board with no credentials still boots fully: the executor holds STOP, and the console, provisioning and self-report stay reachable. Do not reintroduce an `ESP_ERROR_CHECK` around the AI init phase — that is exactly what made the documented no-credentials build boot-loop.

**The Gemini key does not depend on the WiFi source** (issue #845). It is read from NVS (`gemini auth`, namespace `gemini_auth`), then `GEMINI_API_KEY` in `credentials.h`, then the environment. It used to be read from the environment alone once Improv had written WiFi credentials, so provisioning dropped a compiled-in key at once. Released images (CI, web flasher, OTA) carry no key, so a board that is to keep one across an OTA needs it in NVS. `gemini_http.c` notes every status in `gemini_key_state.c`: 401/403 read as `rejected`, 402 as `exhausted`, and the self-report's `gemini_key=` word, `trace` and `gemini` show it.

NVS stores runtime-provisioned credentials — don't wipe NVS unless you want to re-provision.

## OTA

`ota_manager.c` polls the web-flasher's published manifest — `https://laurigates.github.io/mcu-tinkering-lab/firmware/robocar/manifest.json`, generated by `tools/generate-flasher-manifests.sh` on every `build-firmware.yml` release — rather than the GitHub Releases API (issue #539: the API host was wrong, the filename match could never hit, and monorepo release-please tags don't parse as semver; none of that was fixable by configuration alone, and esp_ghota is gone from this project). `version.txt` is the single source of truth for the running version (read at CMake-configure time into `PROJECT_VER`). Release-please manages version bumps — do not edit `version.txt` manually.

Firmware up to 0.2.23 was built as `robocar-unified`: it polls `firmware/unified/manifest.json` and listens on `robocar-unified/ota/notify`. The Pages assembly step in `build-firmware.yml` publishes a copy of `firmware/robocar/` at `firmware/unified/`, so those robots take one update at their periodic check; nothing publishes the old notify topic.

A dedicated FreeRTOS task (`OTA_TASK_STACK_SIZE` = 8192, per `.claude/rules/freertos-task-gotchas.md`'s ≥8 KB rule for any task making an HTTPS call) runs its first check `OTA_FIRST_CHECK_DELAY_MS` (15 s, `ota_interval.h`) after it starts on the boot's first link-up, then blocks on either the `OTA_CHECK_INTERVAL_MIN` (360 min) periodic timeout or an explicit `xTaskNotifyGive()` — the MQTT check-now nudge on `OTA_MQTT_NOTIFY_TOPIC` (`robocar/ota/notify`, rate-limited to one trigger per 60 s) calls `ota_manager_check_update()`, which wakes the task immediately instead of waiting out the interval. Either wake reason runs the same check: fetch the manifest, compare its `version` against `esp_app_get_description()->version` **numerically** (`ota_version_compare.c` — "0.2.10" is newer than "0.2.9", which a lexical compare gets backwards) and its `buildSha` against the running build's (below), and on a newer remote version resolve the manifest's app-binary part **relative to the manifest's own URL** (never a second hardcoded copy of the Pages path) and hand that URL to `esp_https_ota()`. The app part is identified as whichever `parts[]` entry has the highest `offset` — always the app binary, since bootloader/partition-table/otadata sort below it — so the firmware never needs to know a project's `appBinaryName` from a `flasher.json` it doesn't read. The first check used to wait out the full interval, and every reset restarted it, so a robot reset more often than every six hours (13 brownouts on 2026-11-09) never checked at all (issue #1055); `ota_interval_next_wait_ticks()` and `test_ota_interval.c` pin the short first wait.

The `{"status":"downloading"/"rebooting"/"failed"}` publishes on `OTA_MQTT_STATUS_TOPIC` and the 60 s stability timer calling `esp_ota_mark_app_valid_cancel_rollback()` are unchanged from before this rewrite (since issue #846 the manager, and so the stability timer, starts on the first link-up of a boot rather than only when WiFi was up at boot) — rollback protection is load-bearing and was never in question.

**Version comparison fails CLOSED.** A NULL, empty, or non-numeric version on either side (manifest or running firmware) returns "no update" and logs it — never guesses. See `ota_version_compare.h` and its host tests (`just robocar::test`).

**The manifest also names the commit the binary was built from, and the firmware knows its own** (issue #627). `build-firmware.yml` rebuilds every flasher-enabled project at the commit of whichever release fired it, so when another project releases, the `robocar.bin` on Pages is rebuilt from a later commit while `version.txt` still names the last robocar release — the same version string over different contents. `tools/generate-flasher-manifests.sh` writes that commit into every manifest as `buildSha` (a top-level field ESP Web Tools ignores), and the project `CMakeLists.txt` compiles the commit it was configured at into `ota_manager.c` as `ROBOCAR_BUILD_SHA` — 40 hex digits, the same with `-dirty` for a tree with uncommitted changes to tracked files, or `unknown` when git could not read the checkout. The boot log prints it beside the version.

`ota_update_decision.c` combines the two, and the SHA never authorises an install on its own:

| Manifest vs running | Result |
|---|---|
| newer version, valid `buildSha` | install |
| same version, same SHA | up to date |
| same version, different SHA | **refused** — installing would put unreleased commits on the robot under a released version's name |
| same version, running SHA `unknown`/`-dirty` | not installed; nothing to compare against, so a local build is never overwritten by a release of the same version |
| older version | not installed (no downgrades) |
| no `buildSha`, or not 40 lowercase hex | **refused**, whatever the version (fail closed) |

The two refusals also publish `{"status":"refused","reason":"sha_mismatch"|"manifest_sha_missing","version":"…"}` on `OTA_MQTT_STATUS_TOPIC`, since a board off the serial cable has no other way to say it. Expect `sha_mismatch` after most releases of *other* projects: the SHA is repo-wide, so it changes even when nothing under `packages/robotics/robocar/` did. Pinned by `test_ota_update_decision.c`, mutation-checked by deleting the missing-SHA refusal and by turning the mismatch into "up to date".

Two gates keep the two halves naming the same commit, and both must stay. `build-firmware.yml`'s *Verify manifest build SHA* step requires every manifest's `buildSha` to be the tag checkout's `HEAD`, and — for every `flasher.json` declaring `"embedsBuildSha": true` — requires the published app binary to contain that SHA NUL-terminated (`tools/check-embedded-build-sha.py`; a `-dirty` string contains the SHA as a prefix and is rejected). `_ci-build-esp32.yml` runs the binary half on every PR. The failure they exist for is silent: CI builds run in the `espressif/idf` container as root against a runner-owned checkout, git refuses that as "dubious ownership", and the build still succeeds with `unknown` embedded. The CMake lookup passes `-c safe.directory=*` for exactly this, verified against the v5.4 image (plain `rev-parse` exits 128 there, the safe-directory form returns the SHA).

The commit is read at configure time, like `PROJECT_VER`. A new commit re-runs configure (the git `HEAD` file and branch ref are `CMAKE_CONFIGURE_DEPENDS`); an uncommitted edit after configuring does not add `-dirty` until the next configure. A build from a git worktree inside the container embeds `unknown`, because the worktree's `.git` file points at a host path the container cannot see.

### Before the install: announce, postpone, park

A newer version is not installed the moment it is found. `announce_and_park()` in `ota_manager.c` runs first:

1. **A quiet moment.** It waits until no voice turn is running, no conversation window is open and nothing is playing (`OTA_QUIET_WAIT_MS`, 10 min). Past that it gives up until the next check and publishes `deferred_busy`.
2. **What is coming.** `gemini_backend_announce_update()` turns the manifest's `notes` (the version's changelog entries, written by `tools/changelog-notes.py` in `generate-flasher-manifests.sh`) into at most two spoken sentences in the persona's voice. If the request fails, or the manifest predates `notes`, it says `ota_announce_fallback()`: the version only. Then it says `OTA_ANNOUNCE_PUN`, "Menen tuonne toisaalle vähän päivettymään.", verbatim (päivittyä is to update, päivettyä to get a tan). Publishes `announced`.
3. **A minute to postpone.** After the speech has played, `ota postpone` (console or MQTT) defers the install to the next check for `OTA_ANNOUNCE_WINDOW_MS`. Publishes `postponed`.
4. **Open floor.** `ota_park.c` turns in 250 ms steps, stopping 700 ms after each so the smoothed front reading describes that heading, until the front rangefinder sees at least 80 cm. If something is closer than 30 cm behind, it moves forward for 400 ms. A failed front sensor stops it where it is, and after 16 steps it gives up and stays. The turns and the nudge are manual leases, so the obstacle reflex still applies. Publishes `parked`.
5. **Hold still.** `reactive_controller_set_hold(true)` coasts the wheels every executor tick, ahead of the reflex, any lease and the goal, and never expires. The PCA9685 has its own supply and keeps its last outputs through an ESP32 reset, so the wheels have to be stopped before the reboot rather than by it. A failed download releases the hold and says `OTA_ANNOUNCE_FAILED_FI`/`_EN`; the running image is untouched, because the download went to the other slot.

Pinned by `test_ota_park.c` (no open heading, a sensor failing mid-turn, a wall behind, the millisecond wrap), `test_ota_announce.c` (notes dropped whole, UTF-8 never split, a late postpone refused, the wrap) and the hold cases in `test_reactive_controller.c`. **Not yet on a board:** the turning step and nudge lengths are guesses for this chassis, and `ota` prints the phase so a bench run can watch it.

The manifest buffer is 4096 bytes. Firmware up to 0.2.17 holds 2048 and cannot parse a manifest cut short, which is why `changelog-notes.py` caps `notes` at 800 bytes.

**Unverified on device.** Nothing here has taken a real OTA update on a board — that needs hardware and the published manifest's binary to actually flash and boot, which is bench work.

Partition layout is OTA-capable (see `partitions.csv`) with app rollback enabled.


## Don't

- Don't commit `main/credentials.h` — it's gitignored; use the `.example` as template
- Don't hand-edit `version.txt` — release-please owns it
- Don't let a matching or differing build SHA start an OTA install, and don't drop `-c safe.directory=*` from the `CMakeLists.txt` git lookup. Only a strictly newer version installs (the SHA qualifies an equal version and refuses a manifest without one), and without the safe-directory flag every CI binary embeds `unknown` while still building green — see the OTA section
- Don't call `improv_wifi_send_*()` without a writer set, and don't install the usb_serial_jtag driver to send Improv replies. The component's default is UART0, whose TX here carries the log mirror to J15, not the console; driver mode makes console reads block, which stops `command_task`'s 1 Hz Improv announcement. `improv_console_write()` is the transport — see WiFi provisioning
- Don't add a console byte to the line buffer, or log it, when `improv_wifi_process_byte()` returned true for it: an Improv packet can carry the Wi-Fi password. `console_line_feed()` does this; keep `command_task` building lines through it, passing it `s_improv_session` and the byte's read time rather than calling the parser itself, and change the armed state only by bumping `s_improv_session`, so every edge is seen and a packet in flight across it is finished (#1087). Keep `CONSOLE_LINE_BURST_GAP_MS` above command_task's EOF sleep (`main.c` asserts twice `TASK_DELAY_SHORT_MS`)
- Don't move MQTT client creation (`create_mqtt_client()`) after `start_network_supervisor()`, and don't make `mqtt_logger_init()` start the client: the supervisor's first link-up subscribes OTA before it starts MQTT, and a subscription made before `mqtt_logger_init()` is refused (#1054). Check `mqtt_logger_subscribe()`'s return
- Don't announce a hard-coded Improv state; call `improv_wifi_announce()`, and end a failed attempt with `improv_wifi_fail_provisioning()`
